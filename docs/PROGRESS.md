## 〇、这是什么项目

一个语言表达练习应用：**AI 扮演一个"不懂的人"，用户把看过的内容讲给他听——他听懂了，你就讲明白了。**

不打分、不打卡、不教结构套路。表达的本质是"被听懂"，所以用"换一个不懂的人来听"替代评分。

**用户**：梁斌（泰山学院学生）
**产品名**："讲给朋友听"只是**工作名**，未定名。

## 二、V0.5 在干什么（**最重要的一节**）

**一轮迭代里做了三件事**（完整版见 `docs/prd/V0.5-内容与角色.md`）：

### ① 内容形态 —— 治"内容干"

**钩子标题 → 现象 → 对照 → 答案 → 末尾点出名词**

```
[AI 名词] 你少说两句，它多写三页废话

你跟 AI 说「帮我写个总结」，它给你一坨。
你要是说「把这份记录压成五条要点，每条不超过二十个字」，它给的就能直接用了。
同一件事，只是你多说了一句话。
说白了就一条：它看不到你脑子里那一版。你写得越具体，它猜的余地越小。
你发给它的那段话，就叫提示词（Prompt）。
```

⚠️ **走过一段弯路，别重犯**：第一版做"**给一半留一半**"（材料不给结论），实测当场被推翻——用户：

> **"我也不知道为什么差这么多，我还是要教小问的，我感觉挺别扭的"**

**论证**：产品的根是费曼技巧——"发现自己没懂"是**讲出来的后果**，不是材料的坑。
**把"后果"提前做成了"前提"，就变成"她在考我"。**

### ② 会话分段（甲方案）—— 治"乱"

**一条材料一段对话**，左侧抽屉当导航；她递下一张 → 自动切到新一段。

**跟 V0.3 那条决策顶着**（V0.3 定过"对话只有一条，换材料不清空"），**但解得开**：
V0.3 怕的是"有多个小问"，而怕的根源是"**记忆各记各的**"——
**记忆现在是全局的**，所以：**小问始终是一个，但聊天可以分成很多段。**

### ③ 角色定位 —— 治"别扭"

用户原话：

> "**我的问题没有得到立刻解答**，这让我觉得让我去教小问好像不太合适，
> 小问应该能帮我**快速理清我困惑的点**"

**根因**：提示词里"**她不懂**"这个设定出现 **3 次**，"要帮上忙"只有 **1 次**——**权重完全反了**。

**改法**：她懂行、直接答；**去掉所有"教"字**（5 处）。

⚠️ **但没做"完全对换"**——那会让跟豆包的差异表整个塌掉。
**保留的那一条**：你讲一遍给她，她用一个"**没接触过的人能不能跟上**"的标准，挑你没讲清楚的地方。

## 三、关键决策（**改之前先看这里**）

### 产品铁律（从头到现在没变）

- **不打分**，用"AI 复述确认"替代
- **AI 是不懂的朋友** —— ⚠️ **V0.5 修正**：她**懂行**了（用户："小问是知识渊博的老师"），
  但她判断的标准仍然是"**一个没接触过的人能不能跟上**"
- **不设打卡 / 计划 / 等级 / 经验值**
- **不点明"师父/徒弟"**，靠对话行为让用户潜移默化感到"我在教她"
  ⚠️ **V0.5 进一步**：连"教"这个字都不要出现——要说"**咱们聊过**""**你跟我讲过**"
- **铁律：她永远在那儿，你来了她高兴，你不来她绝不打扰**（一旦表现"等待/失望"，打卡就回来了）
- **留存靠"关系"不靠打卡**

### V0.5 九条最容易踩错的

| # | 决策 | 为什么（**别反着做**） |
|---|---|---|
| 1 | **材料必须给完整答案** | 用户不知道就没法讲；"考用户"是这个产品最别扭的状态 |
| 2 | **标题要钩子，正文要答案** | 这两件事治的是不同的病，别混 |
| 3 | **末尾点出名词** | 读完得知道"这东西叫什么" |
| 4 | **她懂行，但别端着** | 懂行归懂行，别用百科腔、别来"那我直接跟你说"这种过渡话 |
| 5 | **不要说"哦哦我懂了"** | 那是向老师汇报听懂了；朋友之间直接说内容 |
| 6 | **绝对不提"教"** | 要说"咱们聊过""你跟我讲过" |
| 7 | **他说"我没说过/不记得"时别争** | 顺一句"那可能是我记岔了"，把话拉回正题 |
| 8 | **用户求答案时，绝对不递材料** | 那时候递材料就是推卸 |
| 9 | **一段 = 一张材料** | `sendText` 存回复必须用**局部 `seg`**，否则切段会串 |

### 界面 / 交互

- **侧栏（左侧抽屉）**：材料列表 = **段导航**；点哪段显示哪段，不用滚
- **一段 = 一张材料**；点「还没讲的」里任意一条 = 开一段新的
- **材料一次只露一张**，讲过的归入「**你跟她讲过的**」+ 日期 + 她的一句总结
- 材料条**默认展开让你读，一发送就自动收起**
- **打字机**：~24 字/秒，落后超 80 字才加速
- **递材料卡**：她的话**吐完 + 4 秒**才弹（典型回复总延迟 ≈7.3 秒）
- 语音和打字机**同时开始，不做严格对齐**（用户原话："豆包也是字出完了声音还在读"）

### 技术

- 前端 `textContent` 渲染（**topics.json 里不能写 markdown**）
- 记忆 / 历史存后端，**按设备分组**（前端 localStorage 随机串）
- 历史**按材料分段**：`{cur, sessions:{材料id:{messages,at}}}`
- **TTS 必须是"前端按需请求"** —— 静音时后端根本不调，**零消耗**
- 语音和文字都失败**不影响**对方

## 四、对外接口 / 数据结构

```
app/chat.py
  build_system_prompt(topic, learned, remaining, already)  ★★★ 产品的心脏
  chat_stream(messages)     流式调用，yield 正文增量
  display_so_far(raw)       流式渲染时"能显示到哪"（边收边剥标记）
  parse_reply(raw)          剥掉标记 → {text, understood, summary, next_id}
  load_env() / load_topics()

app/tts.py
  synthesize(text, id, key, voice_type, region) → (音频字节, 错误)

app/web.py  PORT = 8100
  GET  /api/topics                        话题列表
  GET  /api/memory?device_id=X            该设备记忆
  GET  /api/history?device_id=X           {cur, sessions}
  POST /api/chat     {topic_id, messages, device_id}  → SSE：
                     data:{"t":"<目前为止能显示的全文>"} … data:{"done":true, reply, understood, summary, next_id}
  POST /api/tts      {text, voice}        → audio/mpeg 二进制
```

**隐藏标记**（用户在界面上永远看不到，后端剥离）：

```
[懂了|她的总结]正文…        ← 开头；她真懂了，附一句口语化总结（≤25 字）
…正文[递材料|编号]          ← 末尾；她主动递的下一张材料
```

**数据结构**

```json
// app/memory.json
{ "<设备id>": { "<材料id>": {"summary": "…", "at": "2026-10-11"} } }

// app/history.json   （V0.5 起：一段 = 一张材料）
{ "<设备id>": { "cur": "<材料id>",
                "sessions": { "<材料id>": {"messages": [...], "at": "2026-10-11"} } } }
```

**TTS 端点**：腾讯云 `tts.tencentcloudapi.com` / `TextToVoice` / `Version 2019-08-23`，走**子账号** key。

## 六、踩过的坑（**新窗口别再踩**）

| 坑 | 事实 |
|---|---|
| **混元瓶颈是"首字延迟"（TTFT），不是生成** | 实测：**首字 19.2 秒**，之后 78 个字 0.6 秒全到。**流式治不了"等十几秒"**。解法是换 TTFT 低的模型（现用 `HUNYUAN_MODEL=hy3`）。**用户说"这个模型先用着，后面再调整"** |
| **TTS 音色** | `501000–501007`、`601008–601014` ✅；`4xxxx` / `502xxx` / `603xxx` ❌ 报 `PkgExhausted`。**千嶂 501006 是男声**（曾被我标错成女声，用户要求保留） |
| **iOS 自动播放限制** | 音频必须在用户手势里"解锁"过。做法：**第一次点发送时**塞一段静音 WAV 播一下 |
| **流式剥标记会撞上正文里的方括号** | 她讲向量时真的会写 `"苹果"变 [1,0.8,0.9]`。做法：**扣住最后一个没闭合的 `[`**，闭合后自动放出来 |
| **发送失败要撤上下文** | 失败的那条 user 消息若不撤掉，会留下**连续两条 user**，把后面几次请求一起带坏 |
| **切段时回复会串段** | `sendText` 存回复必须用**局部 `seg`**（`const seg = history`），不能用全局 `history` |
| **标题变长会让开场白出错** | `shortName()` 靠标题里的「」抠短名；钩子标题没有「」→ 会抠出**整句**。解法：topics.json 每条带 **`name`** 字段 |
| **HTML 会被浏览器缓存** | 改了 `index.html` 后**必须强刷**，否则用户看到旧页面，会误判成"改了没用" |
| **语音默认是关的** | 上线前改成了"默认静音"——语音是最贵的开销（每句回复都合成）。想听的人自己点喇叭，之后会记住。⚠️ 自己自测时发现没声音，是正常的 |

**为什么**：语气比结论更能说明他的取向。新窗口读到原话，判断会准得多。

**几个真实例子，值得保留**：

> "我都问你了什么是微调了，你还说温度的事" —— 极反感答非所问

> **"她猜错是她自己笨我觉得没有必要，她应该是拥有和正常人一样甚至更高一些思维逻辑"**
> —— 直接推翻了初版设计，而且他自己讲清了为什么

> **"我也不知道为什么差这么多，我还是要教小问的，我感觉挺别扭的"**
> —— 一句话推翻了 V0.5 的初版"留白"设计

> **"不要体现你教我的，之前教过我"**
> —— 把"师徒"这层关系也一起去掉了

**反例**：把它写成"用户反馈记忆被硬塞"——信息量少一半。

### 5. 用户会拿手机实测，反馈带截图

他经常甩一张手机截图 + 一两句吐槽。**截图里往往是真 bug，先看图，别急着答。**
而且他截图里的**原话**是最硬的证据——**逐句比对提示词**，往往能直接定位到是哪一条规则写错了。
（V0.5 第三节就是这么定位的：同一张截图里她答得极好的一条，直接证明"不是她不会，是提示词不让她答"）
