## 版本核心目标

V0.1 跑通了机制，V0.2 让人设立住。但这两版都只有**一次**：

> 第一次对话靠"她不懂"就够；**第二次以后，必须靠"她记得你教过什么"**。

所以本期只做一件事：**让小问记住用户教过的东西**，并且——这是关键——**让主界面为"一个朋友"服务，而不是为"一堆卡片"服务**。

V0.2 的界面是「三张卡，每张卡里装一段自己的对话」。这个结构天然长成"三个小问，各记各的"，与"一个朋友记得你教的一切"直接冲突。**所以记忆这件事没法只加功能，必须连界面一起改。**

**明确不做**：内容扩充、情景导入、个性化推荐、社交元素、真人试用验证（属 V0.4）。

## 需求背景（为什么是这版）

| 事实 | 推论 |
|---|---|
| 用户自评第一次讲完"还可以" | "还可以"撑不到第二次 |
| 留存方向已定：靠**关系**，不靠打卡 | 关系需要记忆——"被记住"是回来的理由 |
| 豆包也有记忆，但它的"懂"不是从你这学的 | 差异不在"有记忆"，在**"她记得的是你教她的"** |
| 现有界面：卡片 = 对话容器 | 一张卡 = 一个独立小问，关系被切成三份 |

## 关键决策

> 这一节是本次设计探索的全部结论。改之前先看这里。

### A. 产品层

| # | 决策 | 原因 |
|---|---|---|
| A1 | 卡片上留的是**「小问记住了」这样一句轻量痕迹**，**不挂总结长句** | 话题一多，每张卡挂一句总结，列表就没法看 |
| A2 | 她的**总结由她开口说**，不作为数据贴在卡片上 | 总结是"她说的话"，不是徽章；更像她本人 |
| A3 | **不用「已完成」** | 任务语言 = 打卡，违背"不打卡/不打分"铁律 |
| A4 | **记忆是小问的记忆**，不是卡片/话题的记忆 | 这是根治"三个小问"的关键——材料只是她递给你的一张纸 |
| A5 | **对话只能有一条**，切换材料时对话不清空 | 材料的切换是"对话里发生的事"，不是"换一个会话" |
| A6 | **材料一次只露一张**；讲过的自动归入「小问记住了」 | 主界面长度只跟"还没讲的数量"有关，与内容总量脱钩 |
| A7 | **换材料是静默的**——她不在切换时开口 | ⚠️ **改过一轮**：初版设计成"点开讲过的材料，她开口复述总结"，实测（用户手机截图）变成一串播报，很吵。她的总结只该出现在两处：**听懂那一刻的复述确认** + **「小问记住了」面板** |
| A8 | 换到**没讲过**的新材料，她也不主动说话 | 用户刚换过去还在读正文，她插话就是噪音；用户开口她自然接 |
| A9 | 「收起」动作**保留** | 比"我说完了"按钮自然；用户明确要求保留 |
| A10 | **续话不许硬造联想**——必须续话，但不许"为了联想而联想" | ⚠️ **修订 V0.2 的规矩**：V0.2 写死"必须接联想反问"，实测被逼出"这个 RAG 跟你之前说的 Agent 是一回事吗"这种**明显不成立**的比较，很假。改为：联想到**真的像**的才用；宁可**顺着往下问一个细节** |
| A11 | **她可以主动递下一张材料**（`[递材料\|编号]`），界面弹一张卡给两个出口 | 让"换材料"从**用户的动作**变成**她的邀请**——用户自己点"换个材料"有练习/任务感。两个出口：去看看 / 下次吧 |
| A12 | 「下次吧」由**她开口**回应（"行，那不急。你想讲了再跟我说。"），不是界面冒一块灰字 | 界面文字会把对话生硬截断；拒绝也该是她说的话 |
| A13 | 递材料要**上闸**：同一张只递一次；屏幕上还挂着没处理的就不再弹；讲过的/认不出的不弹 | 否则她可能每轮都递——那就成了催，违背铁律 |

### B. 界面层

| # | 决策 | 原因 |
|---|---|---|
| B1 | **方案甲**：唯一对话流 + 顶部小问常驻条 + 可折展材料条 + 面板 | 从 6 个方案中选定（列表原地长高 / 抽成全屏 / 对话当家 / 上下分栏 / 左右滑卡 / 关系线） |
| B2 | 材料条**默认展开让你读**，**一发送就自动收起** | 讲的时候不该照着念；收起把屏幕让给对话 |
| B3 | 小问常驻条**可点**，打开「小问记住了」面板 | 记忆有一个统一的家，不散在各张卡上 |
| B4 | 「换个材料」与点头像打开**同一个面板**（两区：还没讲的 / 小问记住了） | 一个面板两处入口，不搞两个控件 |

### C. 技术层

| # | 决策 | 原因 |
|---|---|---|
| C1 | 记忆存**后端**（先落 `app/memory.json`，后续换数据库，**接口不变**） | 手机浏览器清缓存是常事，存前端会丢 |
| C2 | 身份用前端 `localStorage` 随机串，**按设备分组** | 试用阶段够用。代价：换浏览器/清缓存 = 换个人 |
| C3 | 「她懂了」的信号：提示词要求 AI 在真懂那一刻输出**用户看不见的标记**，后端剥离并记账 | 前端否则无从知道"懂没懂"。代价：每次"听懂"多一次很轻的接口调用 |
| C4 | 只存**"讲过的 + 她记住的那句话"**，不存完整对话历史 | V0.3 用不着；留着以后再说 |
| C5 | 记忆写入失败 → **静默降级**（对话照常，这次不加） | 存储层的事不摊给用户 |
| C6 | 记忆**注入提示词**（「你已经知道的」）——原计划 3b，**提前到 3a** | 前端已经有记忆了，顺手就能传给后端；不做的话跨话题记忆是死的 |
| C7 | 超时 **30s → 90s**；等超过 8 秒提示变「小问还在想…」 | 混元接口**忽快忽慢**（实测 1.6s ~ 24s，与对话长度无关），30s 的线会偶尔被撞上 |
| C8 | 发送失败时**把那条 user 消息从上下文里撤掉** | 否则失败一次就留下**连续两条 user**，会把后面几次请求一起带坏（实测踩到） |

### 设计过程中走的两段弯路（留档，避免重犯）

1. **初版把对话装进卡片**（点卡片 → 卡片就地长成全屏，对话在卡片里）→ 用户实测反馈"感觉像三个小问，每个小问记一个问题"。根因：卡片成了会话容器。
2. **初版让"换材料时她复述总结"** → 用户实测截图显示变成一串播报（"这个你跟我讲过，我记着是…"），很吵。已删除（见 A7）。

## 数据结构

**后端 `app/memory.json`**（按设备分组）：

```json
{
  "<设备id>": {
    "<材料id>": { "summary": "给它一个目标，它自己拆步骤去干", "at": "2026-10-10" }
  }
}
```

**接口变化**：

| 接口 | 变化 |
|---|---|
| `GET /api/topics` | 不变（还是返回话题列表） |
| `GET /api/memory?device_id=X` | **新增**：按设备 id 返回该设备记忆（只回还在架上的材料） |
| `POST /api/chat` | 请求体新增 `device_id`（**不再传 memory**，后端自己查）；返回**结构化** `{reply, understood, summary, next_id}`——隐藏标记在后端就剥掉了 |

**提示词变化**（`app/chat.py:32` `build_system_prompt()`）：

- 新增「你已经知道的事」区：注入该设备已学会的概念 + 她当时的理解
- 新增规则：**自然地用，别每句都提**；只在真能联想上时才提
- 新增：真懂那一刻输出隐藏标记（后端剥离，用户看不到）

## 实现顺序

```
3a（已实现，2026-10-10）
    界面重写（方案甲全状态）
    + 「懂了」隐藏标记判定
    + 记忆注入提示词 + 她主动递下一张材料
    ↑ 后两条原属 3b，实测中提前——不提前就测不出闭环

3b（已实现，2026-10-10）
    app/memory.json 持久化（按设备分组，原子写）
    + 设备 id（前端 localStorage 随机串，多设备不串）
    + GET /api/memory
    + 隐藏标记的剥离从**前端挪到后端**（chat.py 的 parse_reply），
      接口回结构化字段 {reply, understood, summary, next_id}
```

**已实测通过**（真调混元 + 真落盘）：
① `GET /api/memory` 初始返回 `{}` → ② 讲一段让她懂 → 接口回 `understood: true` +
`summary` + `next_id`，且 `reply` 里**没有残留方括号** → ③ 再拉记忆，`rag` 已在 →
④ `memory.json` 正确落盘。

## 验收标准

| # | 标准 | 结果 |
|---|---|---|
| 1 | 主界面只有**一条**对话流；换材料时对话不清空 | [ ] |
| 2 | 讲完一个材料后，它出现在「小问记住了」，顶部计数 +1 | [ ] |
| 3 | **换材料时她完全不说话**（尤其不念总结） | [ ] |
| 4 | 她的总结只出现在：听懂那一刻的复述、以及面板里 | [ ] |
| 5 | 材料条：默认展开，一发送自动收起 | [ ] |
| 6 | 讲过的材料，下次打开仍在「小问记住了」（关掉浏览器再开也在 → 3b） | [ ] |
| 7 | 讲新材料时，她能自然带上以前学过的概念（跨话题联想） | [ ] |
| 8 | 服务挂掉时，页面**即地显示可重试**，不再把报错当聊天发出来 | [ ] |
| 9 | 手机上：输入框不被键盘顶飞；长对话能滚，输入框钉底 | [ ] |
| 10 | 话题上百条时，主界面仍只有一张材料，面板内部滚动 | [ ] |

## 未决 / 遗留

| 事项 | 说明 |
|---|---|
| **流式输出（streaming）** | ⏳ **记下，后续做**。混元实测 1.6s~24s 忽快忽慢，"小问正在听…"有时候要等十几秒才出字——**这是体验的硬伤**。改法：`chat.py` 加流式接口 → `web.py` 改成 SSE 分块返回 → 前端边收边渲染（标记要边收边剥）。**三个文件都要动，是一次正经改动，不是顺手**。等界面手感定下来再做，排在本版靠后 |
| 递材料卡的形态 | 现在做成**对话流内嵌卡**（不是模态弹窗），理由是不打断对话。用户可要求改回弹窗 |
| 「下次吧」那句台词是前端写死的 | 现在硬编码"行，那不急。你想讲了再跟我说。"。要不要让后端生成，待定 |
| 跨话题联想的自然度 | 提多了假、提少了没效果——要真人反馈（V0.4） |
| 记忆存后端 vs localStorage | 3a 先用 localStorage；试用期若多人共用一条 cpolar 链接，**按设备分组不会串** |
| 换设备/清缓存丢记忆 | 已知代价，试用阶段接受；后续做账号才根治 |
| 真实用户是否在意"她记得" | **本版最大不确定**——要 V0.4 真人试用才知道 |
